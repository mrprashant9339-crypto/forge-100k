# Forge 100K generation worker

This worker consumes Supabase `generation_jobs` using atomic PostgreSQL leases, generates original procedural **blockout** GLBs with Blender, validates the GLB container, and stores the result in the user's private upload area. It does not create production/AAA or game-ready assets.

## Deploy

Build the container from the repository root:

```bash
docker build -f workers/Dockerfile -t forge-100k-worker .
docker run --restart unless-stopped \
  -e SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co \
  -e SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_ONLY_SERVICE_ROLE_KEY \
  -e WORKER_POLL_SECONDS=8 \
  --name forge-100k-worker forge-100k-worker
```

Never expose `SUPABASE_SERVICE_ROLE_KEY` in the browser, GitHub Pages, a public repository, or client logs. Put it in the worker host's secret manager.

## Database migrations

Apply these in order in Supabase SQL Editor:

1. `supabase/schema.sql`
2. `supabase/migrations/202611190001_platform_assets.sql`
3. `supabase/migrations/202611190002_worker_queue.sql`

The queue migration adds atomic `FOR UPDATE SKIP LOCKED` claiming, 15-minute renewable leases, bounded retries and service-role-only completion functions. The worker is safe to run as multiple replicas.

## Queue a character blockout job

An authenticated client may insert a row into `public.generation_jobs` with `status='queued'`, `job_type='character'` and a request shaped like:

```json
{
  "asset": {
    "asset_id": "FG-HUM-000042",
    "archetype": "field-explorer",
    "species": "human",
    "style": "armored",
    "seed": 420042,
    "quality_tier": "blockout",
    "target": "glTF2",
    "provenance": {
      "kind": "original_procedural",
      "creator": "Forge 100K",
      "source_url": null,
      "license": "CC0-1.0",
      "license_evidence": "Original procedural geometry generated by this repository"
    }
  }
}
```

The job's `user_id` must be the authenticated user's ID. Asset IDs must be unique. The worker validates the request against the repository's batch-manifest schema before running Blender.

## Current scope and hard boundaries

- Implemented worker type: `character` blockout generation only.
- This worker claims only `character` jobs. Other job types remain queued until their dedicated workers are deployed.
- Output remains `pending_review` in a private bucket; this worker never publishes assets.
- GLB validation is structural/container validation, not artist review, rig/animation certification, collision QA or target-engine certification.
- The worker uses a temporary isolated job directory, enforces a 50 MiB output cap, and never accepts client-supplied filesystem paths or shell commands.
- Production uploads still need malware scanning, visual review, provenance review and a separate publishing service.
